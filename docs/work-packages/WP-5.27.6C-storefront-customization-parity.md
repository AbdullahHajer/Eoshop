## الهدف وحدود السلطة

يكمل هذا العمل تدقيق التكافؤ بعد إغلاق واجهة «تهيئة متجري». مصدر الحقيقة يبقى `StoreConfig` وعقد `marketingBlocks` المحفوظين عبر مسار Workspace ذي الـrevision؛ وتستخدم المعاينة والواجهة المنشورة renderer ومسارات التجارة المشتركة نفسها.

- لا API أو Migration أو جدول أو dependency أو مخزن إعدادات جديد.
- لا تُنشأ وعود تسويقية أو بيانات كتالوج أو دفع غير موجودة في الإسقاط الخادمي.
- لا تُغير هذه الحزمة حدود الأصول المدارة أو قواعد العزل والجدولة والإفصاح المعتمدة في ADR 0039 وADR 0040.
- لا يُعد نجاح الاختبارات أو المراجعة الحية منجزًا حتى تُسجل نتيجته الفعلية في هذه الوثيقة.

## نطاق التنفيذ الجاري

### 1. ملكية أقسام الرئيسية

- يعاد تطبيق `homeSections` كسلطة الترتيب والإظهار الوحيدة للأقسام الخمسة: `hero` و`trust` و`categories` و`featured_products` و`about`.
- يملك كل قسم ظاهر wrapper واحدًا فقط يحمل `data-storefront-section` وفق ADR 0027، ولا يعيد أي قالب إظهار محتوى قسم مخفي داخل قسم آخر.
- في Elegant، يملك `hero` المقدمة ومشهد القصص، وتملك `categories` شريط Discovery. إذا لم توجد قصص فعالة يبقى Hero البديل الصادق قابلًا للعرض بدل مساحة قصص فارغة.
- في Tech، تفصل حدود Hero وCategory rail وDiscovery وما يليها بحسب الدلالة المحفوظة مع إبقاء المظهر المتجاوب للقالب.
- عندما يكون قسما `hero` و`categories` ظاهرين في Tech، يبقى لكل منهما wrapper دلالي مستقل، ويجمعهما غلاف عرض واحد يعيد التركيب المعتمد: التصنيفات يسارًا، Hero/Bento وسطًا، الإعلانات يمينًا، وDiscovery أسفل المجموعة. على الجوال تتحول السكة ودوائر الاكتشاف إلى مسارات أفقية متجاوبة.

### 2. هوية الهيدر والتنقل

- يحترم هيدر القالبين نوع الشعار وحجمه وبيانات الاتصال التي يسمح بها العقد، مع fallback نصي صادق عند غياب أصل صالح.
- تتطابق تسميات التنقل مع الصفحات الموجودة فعليًا، وتُشتق تسمية التصنيفات من الكتالوج المنشور بدل تسمية ثابتة لا تصف المتجر.
- يقيّد القالبان حجم الشعار بين 24 و120 بكسل، ولا يعرضان صورة محفوظة عندما يختار التاجر نوع الشعار الأيقوني.
- تعكس `aria-current` الصفحة الفعلية في الرئيسية والمنتجات والتفاصيل والمعلومات؛ وتُعامل صفحة تفاصيل المنتج كتابع لصفحة المنتجات، ولا تبقى الرئيسية محددة أثناء التنقل.

### 3. محرر المساحات التسويقية

- يعرض المحرر حقولًا تؤثر فعلًا في renderer المختار فقط، ويشرح أن عناصر `discovery` صور تحريرية مشتركة وليست بطاقات منتج بسعر وسلة.
- يخفي محررا Tech وElegant عن عناصر `discovery` حقول CTA والوصف والألوان والتعتيم التي لا يستهلكها العرض، مع إبقاء الصورة وalt والهدف والشارة والإفصاح والراعي ونقطة التركيز.
- تطبق قصص Elegant ملكية الأصل الصحيح، ونوع المحتوى والهدف والإفصاح عن الإعلان/الرعاية وفق العقد المشترك.
- لا يسمح مسار رابط خارجي بإخفاء الإفصاح المطلوب، ولا يعرض المحرر تحكمًا يوحي بسلوك لا تنفذه الواجهة العامة.

### 4. إغلاق فجوات Checkout

- يجمع العنوان `city` و`area` و`details` بوضوح؛ المدينة والمنطقة مطلوبتان، وتصبح التفاصيل مطلوبة فقط عندما يفرض إعداد المتجر ذلك.
- تبقى اقتراحات المدن مساعدة لا قائمة مغلقة، ويُرسل العنوان نفسه إلى الطلب والإيصال والطباعة دون قيمة عامة مضللة.
- يظهر حقل الكوبون ولا يُرسل `couponCode` إلا عندما تكون الكوبونات مفعلة. يحتفظ الإسقاط العام بإشارة القدرة فقط بينما تبقى تعريفات وأكواد الخصم غير عامة.
- تُمسح حالة الخصم المرئية عند تعديل الرمز أو تعطيل القدرة، ولا تُرسل ملاحظات عميل قديمة بعد تعطيل حقل الملاحظات.
- تميز التسميات بين التحويل البنكي والمحافظ الرقمية وعرضهما المشترك، مع إبقاء نوع الدفع الخادمي الحقيقي في الطلب.
- تعرض نتيجة الطلب الحي نجاح الاستلام الحقيقي، بينما تصف المعاينة نفسها بوضوح كمعاينة في القالبين، وتخفي مشاركة WhatsApp وتطبع نموذجًا موسومًا بأنه غير مرسل.

### 5. صدق روابط التواصل

- تتحول الحسابات الاجتماعية المنشورة إلى روابط HTTPS معروفة فقط، وتُرفض القيم غير الصالحة بدل إنشاء وجهة تخمينية أو قابلة للحقن.

## معايير القبول

1. يثبت اختبار القالبين أن ترتيب وإخفاء `homeSections` يعمل على كل قسم دلالي دون تسرب محتوى.
2. يثبت اختبار الهيدر الهوية، fallback، وتحديد الصفحة الحالية في مسارات الواجهة المشتركة.
3. يثبت اختبار المحرر تطابق الحقول الظاهرة مع سلوك `marketingBlocks` وقواعد الهدف والإفصاح.
4. تثبت اختبارات Checkout العنوان الكامل، التفاصيل المشروطة، تعطيل الكوبون، وتسمية طرق التحويل.
5. يثبت اختبار الطلب الفرق بين رسالة المعاينة ورسالة الإرسال الحي.
6. تنجح الاختبارات المركزة، حزمة Frontend الكاملة، TypeScript، Vite build، `npm audit` و`git diff --check` قبل تحويل PR إلى Ready.
7. تُراجع المعاينة والواجهة العامة للقالبين بصريًا على سطح المكتب والجوال قبل الدمج، ويُسجل الدليل الفعلي فقط.

## خارج النطاق والمتابعة اللاحقة

هذه الفجوات مثبتة لكنها لا تُعد منجزة في WP 5.27.6C، وتحتاج حزمًا لاحقة مستقلة:

- **استمرارية Onboarding وصدق التحكم:** إما حفظ كل تحكم ظاهر في المسودة المركزية ثم provisioning، أو حجب التحكم المتقدم حتى يصبح المتجر قائمًا؛ لا تُعرض حقول تُفقد عند الانتقال.
- **تكافؤ تحقق draft/live:** توحيد دلالات التحقق بين مسودات الإنشاء/التصحيح و`StoreWorkspaceContract` الفعلي، بما يشمل الاتصال، الدقة، الكوبونات، الحملات والتخطيط، مع اختبارات تكامل خادمية.
- **إنشاء حملة كمسودة محلية:** تصميم حالة إنشاء قابلة للتحرير لا تنتج فورًا block ناقص الصورة وغير قابل للحفظ، مع قواعد إلغاء واستعادة واضحة.
- **الأداء والـvisual tokens:** تقسيم حزمة JavaScript التي تتجاوز تحذير Vite، ثم حصر الألوان والمسافات الثابتة وتحويلها إلى tokens مشتركة دون خلط ذلك بإصلاحات السلوك الحالية.
